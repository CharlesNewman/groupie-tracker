## 1. Κατάνοηση API, JSON & REST Architecture

Για να καταλάβουμε πώς θα αλληλεπιδράσουμε με τα δεδομένα του project, πρέπει να κατανοήσουμε τις βασικές έννοιες της δικτυακής επικοινωνίας λογισμικού:

### 1.1 Τι είναι το API (Application Programming Interface);
Το **API** (Διεπαφή Προγραμματισμού Εφαρμογών) είναι ένα σύνολο από κανόνες, πρωτόκολλα και εργαλεία που επιτρέπουν σε διαφορετικές εφαρμογές λογισμικού να επικοινωνούν μεταξύ τους. 
* Στην περίπτωσή μας, ο δημιουργός του API έχει στήσει έναν εξωτερικό server που περιέχει τη βάση δεδομένων με τους καλλιτέχνες, τις τοποθεσίες και τις ημερομηνίες.
* Εμείς (μέσω της Go εφαρμογής μας) λειτουργούμε ως "καταναλωτής" (client) αυτού του API: στέλνουμε αιτήματα (HTTP requests) και παίρνουμε πίσω δεδομένα.

### 1.2 Πώς λέγεται αυτή η επικοινωνία & τι χρησιμοποιείται συνήθως;
Η επικοινωνία αυτή βασίζεται στο αρχιτεκτονικό μοντέλο **REST** (Representational State Transfer) και τα APIs αυτού του τύπου ονομάζονται **RESTful APIs**:
* **Πρωτόκολλο Επικοινωνίας**: Χρησιμοποιείται το **HTTP/HTTPS**.
* **Endpoints**: Κάθε διαθέσιμη πληροφορία είναι προσβάσιμη μέσω συγκεκριμένων διευθύνσεων URL (π.χ. `https://.../api/artists`).
* **HTTP Methods (Ρήματα)**:
  * `GET`: Για ανάκτηση/ανάγνωση δεδομένων (αυτό που χρησιμοποιούμε αποκλειστικά στο Groupie Trackers)[cite: 1].
  * `POST`: Για δημιουργία νέων δεδομένων.
  * `PUT` / `PATCH`: Για ενημέρωση/τροποποίηση δεδομένων.
  * `DELETE`: Για διαγραφή δεδομένων.
* **HTTP Headers & Content-Type**: Πληροφορίες που συνοδεύουν το αίτημα ή την απάντηση. Όταν ζητάμε JSON δεδομένα, ο διακομιστής απαντά με header `Content-Type: application/json`[cite: 1].
* **HTTP Status Codes**:
  * `200 OK`: Επιτυχής κλήση.
  * `400 Bad Request`: Λανθασμένο αίτημα από τον client.
  * `404 Not Found`: Το endpoint ή ο πόρος δεν υπάρχει.
  * `500 Internal Server Error`: Σφάλμα στον server.

### 1.3 Τι είναι το JSON (JavaScript Object Notation);
Το **JSON** είναι μια ελαφριά μορφή ανταλλαγής δεδομένων (data-interchange format) που διαβάζεται εύκολα τόσο από ανθρώπους όσο και από μηχανές. 
* Είναι ανεξάρτητο γλώσσας προγραμματισμού, γι' αυτό χρησιμοποιείται σχεδόν καθολικά στα REST APIs.
* Υποστηρίζει βασικούς τύπους δεδομένων: συμβολοσειρές (strings), αριθμούς (numbers), Booleans (`true`/`false`), πίνακες (arrays `[]`) και αντικείμενα (objects `{}`).

### 1.4 Τα 4 Endpoints του Groupie Trackers API:
* `/artists`: Λίστα με καλλιτέχνες/μπάντες (όνομα, εικόνα, έτος έναρξης, πρώτο άλμπουμ, μέλη)[cite: 1].
* `/locations`: Τοποθεσίες συναυλιών ανά καλλιτέχνη[cite: 1].
* `/dates`: Ημερομηνίες συναυλιών ανά καλλιτέχνη[cite: 1].
* `/relation`: Συσχέτιση (map) μεταξύ τοποθεσιών και ημερομηνιών για κάθε καλλιτέχνη[cite: 1].

### 1.5 JSON Unmarshaling στη Go
Στη Go, η διαδικασία μετατροπής ενός κειμένου/stream JSON σε δομές δεδομένων (structs) της Go ονομάζεται **Unmarshaling** (ή Decoding).
* Χρησιμοποιούμε το πακέτο `encoding/json`[cite: 1].
* Ορίζουμε **Struct Tags** (π.χ. `` `json:"creationDate"` ``) ώστε η Go να γνωρίζει ποιο πεδίο του JSON αντιστοιχεί σε ποιο πεδίο του `struct`[cite: 1].

### Δομές Δεδομένων (Structs) σε Go:

```go
package models

// ── domain structs for API data ───────────────────────────────────────────── ⊃

// Artist represents the core information of a band or musical group.
type Artist struct {
	ID           int      `json:"id"`
	Image        string   `json:"image"`
	Name         string   `json:"name"`
	Members      []string `json:"members"`
	CreationDate int      `json:"creationDate"`
	FirstAlbum   string   `json:"firstAlbum"`
	Locations    string   `json:"locations"`
	ConcertDates string   `json:"concertDates"`
	Relations    string   `json:"relations"`
}

// RelationIndex represents the root wrapper for relation API responses.
type RelationIndex struct {
	Index []Relation `json:"index"`
}

// Relation links concert locations with their respective dates.
type Relation struct {
	ID             int                 `json:"id"`
	DatesLocations map[string][]string `json:"datesLocations"`
}

// CombinedArtist holds fully hydrated artist details with relations merged.
type CombinedArtist struct {
	Artist    Artist
	Relations map[string][]string
}
```

Το API του Groupie Trackers αποτελείται από 4 βασικά endpoints:
* `/artists`: Λίστα με καλλιτέχνες/μπάντες (όνομα, εικόνα, έτος έναρξης, πρώτο άλμπουμ, μέλη).
* `/locations`: Τοποθεσίες συναυλιών ανά καλλιτέχνη.
* `/dates`: Ημερομηνίες συναυλιών ανά καλλιτέχνη.
* `/relation`: Συσχέτιση (map) μεταξύ τοποθεσιών και ημερομηνιών για κάθε καλλιτέχνη.

### Τι πρέπει να μάθουμε:
1. **HTTP Client στη Go (`net/http`)**: Πώς κάνουμε `http.Get(url)` για να κατεβάσουμε τα δεδομένα από το εξωτερικό API.
2. **JSON Struct Tags (`encoding/json`)**: Πώς αντιστοιχίζουμε τα πεδία του JSON (`json:"name"`) στα structs της Go.

### Δομές Δεδομένων (Structs) σε Go:

```go
package models

// ── domain structs for API data ───────────────────────────────────────────── ⊃

// Artist represents the core information of a band or musical group.
type Artist struct {
	ID           int      `json:"id"`
	Image        string   `json:"image"`
	// κλπ
}
```

## 2. Συσχέτιση & Διαχείριση Δεδομένων (Data Merging)

Στο Groupie Trackers, το API δεν προσφέρει όλα τα στοιχεία ενός καλλιτέχνη σε ένα έτοιμο πακέτο. Επιστρέφει τα βασικά στοιχεία, τις τοποθεσίες, τις ημερομηνίες και τις σχέσεις μεταξύ τους σε 4 διαφορετικά endpoints[cite: 1]. 

Η κύρια δουλειά του backend (Go) είναι να λειτουργήσει ως **Data Aggregator** (συλλέκτης & συνθέτης δεδομένων) πριν στείλει την πληροφορία στα HTML templates[cite: 1].

### 2.1 Γιατί η σύνθεση (Merging) πρέπει να γίνει στον Server;
1. **Απόδοση (Performance)**: Εάν ο browser (client) έκανε ξεχωριστά requests για κάθε καλλιτέχνη και για κάθε endpoint, η σελίδα θα καθυστερούσε υπερβολικά και θα επιβάρυνε το δίκτυο.
2. **Καθαρή Αρχιτεκτονική**: Το frontend πρέπει να παραλαμβάνει έτοιμες, καθαρές δομές δεδομένων και να εστιάζει μόνο στην εμφάνιση (UI), αφήνοντας τη λογική επεξεργασίας στο backend[cite: 1].

### 2.2 Η Πρόκληση της Δομής του `/relation`
Το endpoint `/relation` συνδέει τις τοποθεσίες με τις αντίστοιχες ημερομηνίες συναυλιών[cite: 1]. Η δομή του χρησιμοποιεί ένα δυναμικό χάρτη (map):
* Το **ID** του καλλιτέχνη αντιστοιχεί σε ένα αντικείμενο.
* Μέσα στο αντικείμενο, τα **keys** είναι οι τοποθεσίες (π.χ. `north_carolina-usa`) και τα **values** είναι πίνακες με αλφαριθμητικά ημερομηνιών (π.χ. `["23-08-2019", "25-08-2019"]`)[cite: 1].

### 2.3 Θεωρητικά Βήματα Υλοποίησης (Algorithm Logic)
Για να πετύχετε το Data Merging στη Go, ακολουθείτε τα εξής στάδια:

1. **Ανάκτηση (Data Fetching)**: Εκτελείτε HTTP GET requests προς τα endpoints `/artists` και `/relation`[cite: 1].
2. **Μετατροπή (Deserialization)**: Μετατρέπετε τα JSON δεδομένα σε Go structs με τη χρήση του `encoding/json`[cite: 1].
3. **Δημιουργία Ευρετηρίου (Indexing)**: Για να μην ψάχνετε διπλά σε κάθε λίστα (που θα καθιστούσε τον αλγόριθμο αργό, $O(n^2)$), μετατρέπετε τις σχέσεις σε ένα Go `map` όπου το key είναι το ID του καλλιτέχνη. Αυτό επιτρέπει την άμεση αναζήτηση σε χρόνο $O(1)$.
4. **Mορφοποίηση Κειμένου (Data Normalization / Sanitization)**: 
   * Τα ονόματα των πόλεων στο API περιέχουν κάτω παύλες (`_`) αντί για κενά και παύλες (`-`) αντί για κόμματα.
   * Κατά τη διάρκεια της συσχέτισης, αντικαθιστάτε αυτούς τους χαρακτήρες ώστε το κείμενο να διαβάζεται φυσικά από τον χρήστη (π.χ. το `new_york-usa` μετατρέπεται σε `New York, Usa`).
5. **Σύνθεση (Consolidation)**: Δημιουργείτε ένα τελικό, ενοποιημένο struct (π.χ. `CombinedArtist`) που περιέχει τα βασικά στοιχεία του καλλιτέχνη μαζί με τον καθαρισμένο χάρτη των συναυλιών του[cite: 1].

## 3. Client-Server Επικοινωνία & Events / Actions

Η εκφώνηση ζητάει την υλοποίηση ενός **Client-Server Event/Action**[cite: 1]. Πρόκειται για τον μηχανισμό που επιτρέπει στη σελίδα να αντιδρά δυναμικά στις ενέργειες του χρήστη[cite: 1].

### 3.1 Τι είναι το Client-Server Event;
Ένα event είναι μια ενέργεια που πυροδοτείται στο περιβάλλον του χρήστη (Frontend)[cite: 1]. Αντί η σελίδα να κάνει πλήρη ανανέωση (full page reload) μέσω μιας παραδοσιακής HTML φόρμας, η ενέργεια αυτή στέλνει ένα **ασύγχρονο αίτημα (AJAX request via `fetch()`)** στον Go server[cite: 1].

Ο κύκλος ζωής της επικοινωνίας:
1. **Trigger (Frontend)**: Ο χρήστης αλληλεπιδρά με κάποιο στοιχείο της σελίδας (π.χ. πληκτρολογεί, επιλέγει ένα φίλτρο).
2. **Request (Client $\to$ Server)**: Το JavaScript "πιάνει" το event και στέλνει ένα ασύγχρονο `fetch()` request με τις παραμέτρους της ενέργειας[cite: 1].
3. **Processing (Server)**: Ο Go server λαμβάνει το αίτημα, εκτελεί τη λογική (π.χ. φιλτράρισμα ή αναζήτηση στη μνήμη) και επιστρέφει τα δεδομένα σε μορφή JSON[cite: 1].
4. **Update (Server $\to$ Client)**: Το JavaScript παραλαμβάνει το JSON και τροποποιεί το DOM (την HTML σελίδα) τοπικά, προσφέροντας μια ομαλή εμπειρία χρήστη (User Experience)[cite: 1].

### 3.2 Ιδέες για το Event που μπορείτε να επιλέξετε

* **Live Search (Αναζήτηση σε πραγματικό χρόνο)**:
  * *Event*: Ο χρήστης πληκτρολογεί χαρακτήρες στο πεδίο αναζήτησης (`input` event)[cite: 1].
  * *Server Logic*: Ο server αναζητά αν η λέξη-κλειδί υπάρχει στο όνομα, στα μέλη, στην πρώτη ημερομηνία άλμπουμ ή στις τοποθεσίες[cite: 1].
  * *UI Result*: Εμφανίζεται αμέσως μια λίστα με προτάσεις κάτω από τη γραμμή αναζήτησης.

* **Dynamic Filters (Δυναμικά Φίλτρα)**:
  * *Event*: Ο χρήστης αλλάζει την τιμή σε ένα εύρος χρονιών (range slider) ή επιλέγει αριθμό μελών[cite: 1].
  * *Server Logic*: Ο server φιλτράρει τη λίστα των καλλιτεχνών βάσει των κριτηρίων[cite: 1].
  * *UI Result*: Οι κάρτες των καλλιτεχνών στην οθόνη εξαφανίζονται/εμφανίζονται στιγμιαία ανάλογα με τα φίλτρα.

* **Modal / Pop-up Λεπτομερειών**:
  * *Event*: Ο χρήστης κάνει κλικ στο κουμπί "Δες Συναυλίες" μιας κάρτας.
  * *Server Logic*: Ο server επιστρέφει αποκλειστικά το relation data για το συγκεκριμένο ID[cite: 1].
  * *UI Result*: Ανοίγει ένα παράθυρο πάνω από τη σελίδα (modal) με τις πληροφορίες, χωρίς ο χρήστης να αλλάξει URL ή σελίδα[cite: 1].

### 3.3 Αρχιτεκτονικά Σημεία Προσοχής
* **Debouncing (Frontend)**: Στην περίπτωση του Live Search, πρέπει να προσέξετε να μην στέλνετε HTTP request σε κάθε μεμονωμένο πάτημα πλήκτρου. Χρησιμοποιείται ένας μικρός χρονοδιακόπτης (debouncer) ώστε το αίτημα να στέλνεται αφού ο χρήστης σταματήσει να πληκτρολογεί για λίγα milliseconds.
* **Content-Type Headers (Backend)**: Ο Go handler που εξυπηρετεί το event πρέπει να θέτει ρητά το HTTP Header: `w.Header().Set("Content-Type", "application/json")` πριν στείλει την απάντηση[cite: 1].
* **Error Handling**: Αν η αναζήτηση δεν βρει αποτελέσματα, ο server πρέπει να επιστρέψει έναν άδειο πίνακα JSON (`[]`) και όχι σφάλμα, ώστε το frontend να εμφανίσει ένα φιλικό μήνυμα (π.χ. "Δεν βρέθηκαν αποτελέσματα").

Η εκφώνηση ζητάει ρητά τη δημιουργία ενός **Client-Server Event/Action**[cite: 1]. Αυτό είναι το κομμάτι όπου η σελίδα μας παύει να είναι απλά "στατική HTML" και αποκτά δυναμική αλληλεπίδραση[cite: 1].

### 3.1 Τι σημαίνει Client-Server Event;
Ένα event είναι μια ενέργεια που συμβαίνει στο frontend (π.χ. ο χρήστης πληκτρολογεί, πατάει ένα κουμπί, αλλάζει ένα slider)[cite: 1]. Η ενέργεια αυτή πυροδοτεί ένα **ασύγχρονο request (AJAX / `fetch()`)** προς τον Go server[cite: 1]. Ο server επεξεργάζεται το αίτημα, επιστρέφει JSON δεδομένα, και το JavaScript στο frontend ενημερώνει την οθόνη **χωρίς να γίνει reload ολόκληρη η σελίδα**[cite: 1].

### 3.2 Πώς λειτουργεί ο κύκλος Request - Response:
```
[ User Action (Frontend) ] ──( JavaScript fetch() )──> [ Go API Endpoint ]
                                                              │
                                                        (Processing)
                                                              │
[ DOM Update (No Reload) ] <──( JSON Response )───────────────┘
```

### 3.3 Προτεινόμενα Events για το Project:

#### Επιλογή Α: Dynamic Search & Live Auto-complete (Προτεινόμενο)
* **Event**: Ο χρήστης πληκτρολογεί στο πεδίο αναζήτησης (`input` event).
* **Action**: Το JS στέλνει request στο `/api/search?q=queen`.
* **Server Logic**: Ο Go server φιλτράρει ονόματα καλλιτεχνών, μέλη, χρονιές και τοποθεσίες συναυλιών.
* **Response**: Επιστρέφεται λίστα με τα αποτελέσματα σε JSON.
* **UI Result**: Εμφανίζεται dropdown με προτάσεις την ώρα που πληκτρολογεί ο χρήστης.

#### Επιλογή Β: Interactive Multi-Filter (Filters Bar)
* **Event**: Ο χρήστης αλλάζει τις τιμές στα φίλτρα (π.χ. Αριθμός μελών: 4, Χρονιά: 1990-2005, Τοποθεσία: USA).
* **Action**: Request στο `/api/filter?members=4&from=1990&to=2005`.
* **Server Logic**: Ο server εκτελεί σύνθετο φιλτράρισμα στη μνήμη.
* **UI Result**: Οι κάρτες των καλλιτεχνών στην οθόνη ανανεώνονται στιγμιαία.

#### Επιλογή Γ: Modal Detail View via AJAX
* **Event**: Κλικ στο κουμπί "Show Concerts" μιας κάρτας.
* **Action**: Request στο `/api/relation?id=1`.
* **UI Result**: Ανοίγει ένα pop-up παράθυρο (modal) που φορτώνει τις ημερομηνίες χωρίς μετάβαση σε άλλη σελίδα[cite: 1].

## 4. Σταθερότητα & Χειρισμός Σφαλμάτων (Crash Prevention)

Στην ανάπτυξη δικτυακών εφαρμογών και web servers, μία από τις σημαντικότερες απαιτήσεις είναι η **διαθεσιμότητα (availability)** και η **ανθεκτικότητα (fault tolerance)**. Ο server πρέπει να είναι σχεδιασμένος έτσι ώστε καμία εσφαλμένη ενέργεια χρήστη, κανένα απρόσμενο δεδομένο και καμία αποτυχία εξωτερικής υπηρεσίας να μην μπορεί να διακόψει τη λειτουργία του (να μην "πέσει" η εφαρμογή).

### 4.1 Η Έννοια του Panic & Recovery
Στη γλώσσα Go, όταν συμβεί ένα κρίσιμο, μη αναμενόμενο σφάλμα κατά την εκτέλεση του προγράμματος (όπως η προσπέλαση ενός δείκτη που είναι `nil` ή η πρόσβαση εκτός ορίων ενός πίνακα), το σύστημα προκαλεί ένα **Panic**. 
* **Τι κάνει το Panic:** Διακόπτει αμέσως τη φυσιολογική ροή του προγράμματος και αρχίζει να ανεβαίνει προς τα πάνω στη στοίβα κλήσεων (stack unwinding). Αν δεν αντιμετωπιστεί, τερματίζει ολόκληρη τη διεργασία του server.
* **Η τεχνική του Recovery:** Μέσω του μηχανισμού ανάκτησης (`recover`), ο server μπορεί να "συλλάβει" ένα panic την ώρα που συμβαίνει, να καταγράψει το σφάλμα στα logs για τους προγραμματιστές και να συνεχίσει να λειτουργεί ομαλά, επιστρέφοντας απλά στον χρήστη μια κατάλληλη σελίδα σφάλματος.

### 4.2 Αρχιτεκτονική Middleware
Το **Middleware** είναι ένα στρώμα λογισμικού που παρεμβάλλεται ανάμεσα στην είσοδο ενός δικτυακού αιτήματος (HTTP Request) και στον τελικό επεξεργαστή του (Handler).
* Λειτουργεί σαν ένα προστήθιο φίλτρο ασφαλείας.
* Κάθε αίτημα περνά υποχρεωτικά μέσα από το Middleware πριν φτάσει στη λογική της εφαρμογής.
* Αν συμβεί οποιοδήποτε απρόοπτο κατά την επεξεργασία του αιτήματος, το Middleware εγγυάται ότι η ζημιά περιορίζεται αποκλειστικά σε αυτό το συγκεκριμένο αίτημα, προστατεύοντας τη συνολική σταθερότητα του διακομιστή.

### 4.3 Διαχείριση Ορίων & Σφαλμάτων Δικτύου (Timeouts & Edge Cases)
Όταν ο server επικοινωνεί με εξωτερικές υπηρεσίες (όπως το API του Groupie Trackers), εξαρτάται από τη συμπεριφορά τρίτων.
* **Δικτυακά Timeouts:** Αν το εξωτερικό API καθυστερήσει να απαντήσει ή "παγώσει", ο server δεν πρέπει να περιμένει επ' αόριστον δεσμεύοντας πόρους του συστήματος. Ορίζονται αυστηρά χρονικά όρια (timeouts), ώστε αν μια κλήση αργήσει, να διακόπτεται με ασφάλεια.
* **Έλεγχος Εισόδου (Input Validation):** Οποιοδήποτε στοιχείο εισάγεται από τον χρήστη μέσω του URL (π.χ. παράμετροι αναζήτησης ή αναγνωριστικά IDs) θεωρείται δυνητικά επικίνδυνο ή λανθασμένο. Ο server οφείλει να ελέγχει αν τα δεδομένα είναι στη σωστή μορφή (π.χ. αν ένα ID είναι πράγματι αριθμός) πριν προσπαθήσει να τα επεξεργαστεί.

## 5. Unit Testing στη Go (`testing` & `httptest`)

Ο **Μοναδιαίος Έλεγχος (Unit Testing)** είναι η πρακτική κατά την οποία δοκιμάζουμε μεμονωμένα κομμάτια του λογισμικού (όπως συναρτήσεις, αλγορίθμους ή handlers) σε απομόνωση, για να βεβαιωθούμε ότι συμπεριφέρονται ακριβώς όπως αναμένεται υπό διάφορες συνθήκες.

### 5.1 Γιατί είναι απαραίτητα τα Unit Tests;
* **Πρόληψη Παλινδρόμησης (Regression Prevention):** Όταν προσθέτουμε νέα χαρακτηριστικά ή διορθώνουμε κάποιο πρόβλημα, τα tests μας επιβεβαιώνουν ότι δεν "σπάσαμε" κατά λάθος κάποια λειτουργία που δούλευε προηγουμένως.
* **Αυτοματοποιημένος Έλεγχος:** Αντί να δοκιμάζουμε χειροκίνητα τη σελίδα στον browser κάθε φορά που αλλάζει κάτι, η σουίτα δοκιμών εκτελείται σε ελάχιστα δευτερόλεπτα.
* **Σχεδιασμός Κώδικα:** Η γραφή δοκιμάσιμου κώδικα μας αναγκάζει να δημιουργούμε μικρές, αυτόνομες και ανεξάρτητες συναρτήσεις με ξεκάθαρους ρόλους.

### 5.2 Η Έννοια του HTTP Testing (Mocking & Recorders)
Όταν δοκιμάζουμε δικτυακές εφαρμογές, δεν θέλουμε να ξεκινάμε έναν πραγματικό server που δεσμεύει πόρτες (ports) ούτε να κάνουμε πραγματικές κλήσεις στο διαδίκτυο κατά τη διάρκεια των τεστ.
* **HTTP Recorders:** Χρησιμοποιούνται εικονικές δομές που προσομοιώνουν την απόκριση του server. Λειτουργούν σαν ένας "καταγραφέας" που αποθηκεύει τους κωδικούς κατάστασης (Status Codes), τα headers και το σώμα (body) της απάντησης για να τα εξετάσουμε.
* **Mock Requests:** Δημιουργούμε πλαστά αιτήματα (π.χ. ένα αίτημα για μια σελίδα που δεν υπάρχει) και ελέγχουμε αν το σύστημα αντιδρά ορθά (π.χ. επιστρέφοντας τον κωδικό 404).

### 5.3 Τι Πρέπει να Καλύπτει μια Σουίτα Δοκιμών:
1. **The Happy Path:** Δοκιμή των σεναρίων όπου όλα λειτουργούν ρολόι (έγκυρα δεδομένα, επιτυχείς αποκρίσεις 200 OK).
2. **Edge Cases & Error Paths:** Δοκιμή οριακών καταστάσεων (π.χ. κενές συμβολοσειρές, αρνητικοί αριθμοί, μη υπαρκτές διαδρομές URL) για να επιβεβαιωθεί ότι το σύστημα επιστρέφει τα σωστά HTTP Status Codes (400, 404, 500) χωρίς να καταρρέει.

## 6. Δομή Project & Κανόνες Κώδικα

Η σωστή οργάνωση των αρχείων και η τήρηση κοινών προτύπων γραφής (coding standards) είναι καθοριστικής σημασίας για την ομαλή συνεργασία μιας ομάδας. Ένα καθαρά δομημένο project επιτρέπει σε όλα τα μέλη να κατανοούν αμέσως πού βρίσκεται η κάθε λειτουργία.

### 6.1 Αρχιτεκτονικά Πρότυπα Οργάνωσης (Standard Project Layout)
Στη γλώσσα Go, η οργάνωση των φακέλων ακολουθεί συγκεκριμένες συμβάσεις της κοινότητας:
* **cmd/:** Περιέχει τα σημεία εισόδου της εφαρμογής (main). Είναι το σημείο από όπου εκκινεί ο διακομιστής και συναρμολογούνται τα επιμέρους εξαρτήματα.
* **internal/:** Περιέχει τον ιδιωτικό κώδικα της εφαρμογής (επιχειρησιακή λογική, μοντέλα δεδομένων, handlers). Ο κώδικας εδώ είναι προστατευμένος και δεν μπορεί να εισαχθεί από εξωτερικά projects.
* **templates/ & static/:** Διαχωρισμός των αρχείων παρουσίασης. Τα templates αφορούν τις δυναμικές δομές HTML, ενώ ο φάκελος static περιλαμβάνει τα στατικά στοιχεία (CSS, client-side JS, εικόνες).
* **docs/:** Ο χώρος τεκμηρίωσης του έργου, όπου αποθηκεύονται οδηγοί αρχιτεκτονικής, σημειώσεις σχεδιασμού και η τεκμηρίωση του API.

### 6.2 Αρχές Καθαρού Κώδικα (Clean Code Principles)
* **Single Responsibility Principle (Αρχή της Μίας Υπευθυνότητας):** Κάθε πακέτο και κάθε συνάρτηση πρέπει να υπηρετεί έναν και μοναδικό σκοπό. Για παράδειγμα, η λογική λήψης των δεδομένων από το API δεν πρέπει να μπλέκεται με τη λογική εμφάνισης της HTML.
* **Explicit Error Handling (Ρητός Χειρισμός Σφαλμάτων):** Στη Go τα σφάλματα δεν αγνοούνται. Κάθε συνάρτηση που μπορεί να αποτύχει επιστρέφει ένα σφάλμα, το οποίο πρέπει να ελέγχεται αμέσως από τον καλούντα.
* **Team Communication via Documentation:** Η συντηρησιμότητα του κώδικα βασίζεται στη σαφή τεκμηρίωση. Τα σχόλια πρέπει να εξηγούν το *γιατί* γράφτηκε κάτι και όχι το *τι* κάνει ο κώδικας (το οποίο φαίνεται από την ίδια τη γλώσσα), διατηρώντας ομοιόμορφο στυλ σε όλη την έκταση του repository.

### Προτεινόμενη Δομή Φακέλων:
```
groupie-trackers/
├── cmd/
│   └── main.go           # Entry point του server
├── internal/
│   ├── handlers/         # HTTP Handlers (Home, ArtistDetail, Search)
│   ├── models/           # Go Structs για τα JSON δεδομένα
│   ├── service/          # API Fetching & Merging logic
│   └── middleware/       # Panic recovery & Logging
├── templates/            # HTML templates (index.html, error.html)
├── static/               # CSS, JS, εικόνες
├── docs/
│   └── LEARNING_GUIDE.md # Ο παρών οδηγός
└── go.mod
```
